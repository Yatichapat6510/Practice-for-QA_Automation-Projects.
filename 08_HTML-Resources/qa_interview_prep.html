Strength: "Deep-dive root cause analysis — I trace logs and query the database to find the actual cause, not just surface-level reports. I also cover a broad range: web, API, performance, and mobile."

HR 04
เล่าสถานการณ์ที่เจอ bug สำคัญในงานให้ฟังหน่อย
Tell me about a critical bug you found.
▾
ใช้ STAR Framework
"ระหว่าง regression test ก่อน release พบว่าตัวเลขใน Excel export ไม่ตรงกับ database (Situation/Task) → query MSSQL trace ที่มาของข้อมูล พบว่า stored procedure คำนวณ aggregate ผิด logic (Action) → แจ้ง Dev พร้อมแนบ query พิสูจน์ทันที ทำให้แก้ได้ก่อน deploy production (Result)"
"During regression testing before a release, Excel export figures didn't match the database. I ran MSSQL queries to trace the data origin and found an aggregation error in a stored procedure. I reported it with the exact query as proof — fixed before it hit production."
💡 ยิ่งบอก impact ได้ชัด (ป้องกัน X, ประหยัด Y) ยิ่งดี — startup ให้คุณค่ากับคนที่คิดแบบ "มีผลลัพธ์จริง"
HR 05
คุณจัดการ pressure / deadline กระชั้นอย่างไร?
How do you handle tight deadlines?
▾
แนวทางตอบ (ไทย)
"เมื่อเจอ deadline กระชั้น จะ triage test cases ก่อนว่าอะไรคือ critical path ที่ต้องทดสอบก่อน แล้วสื่อสารกับ SA/Dev ตรงๆ ว่าสิ่งไหนทดสอบครบแล้ว สิ่งไหนยัง risk อยู่ เพื่อให้ทีมตัดสินใจบนข้อมูลจริง ไม่ใช่แค่รีบ approve ผ่านโดยไม่รู้ความเสี่ยง"
"I triage test cases to identify the critical path first, then communicate transparently with SA/Dev about what's covered and what risk remains — so the team makes informed go/no-go decisions rather than blindly rushing to approve."
💡 Startup ชอบคนที่ "พูดตรง" — การบอก risk ตรงๆ ดีกว่าแกล้งทำเป็นว่าทุกอย่าง ok
HR 06
ทำงานกับ Dev/SA ยังไงเมื่อ requirement ไม่ชัด?
How do you collaborate when requirements are unclear?
▾
แนวทางตอบ (ไทย)
"เมื่อ requirement ไม่ชัด จะไม่รอให้เอกสารครบก่อน แต่จะ list assumption ที่มีแล้วไปคุย SA ทันทีเพื่อยืนยัน ถ้าซับซ้อนจะขอ workshop 15 นาที เพื่อ align ทั้ง 3 ฝ่าย (Dev/SA/QA) ก่อนเขียน test case เพราะการรื้อ test case ที่เขียนผิดทิศนั้นเสียเวลากว่ามาก"
"I don't wait for perfect documentation. I list my assumptions and validate them with the SA immediately. For complex cases, I request a quick 15-minute alignment with Dev, SA, and QA together before writing test cases."
💡 คนที่ "ถามก่อนลงมือ" มีคุณค่ามากกว่าคนที่ทำแล้วรื้อใหม่ทั้งหมด

TECH 01
อธิบาย process เขียน test case ให้ฟัง
Walk me through how you write a test case.
▾
แนวทางตอบ (ไทย)
"เริ่มวิเคราะห์ requirement หรือ user story แล้วแตก test scenario ตาม business flow หลัก แต่ละ test case ประกอบด้วย: precondition, test steps, expected result, actual result นอกจาก happy path จะเน้น boundary value, negative case และ edge case เสมอ เพราะ bug มักซ่อนอยู่ตรงนั้น"
"I analyze the requirement or user story, then break it into test scenarios based on the main business flow. Each test case includes precondition, test steps, expected result, and actual result. Beyond the happy path, I always cover boundary values, negative cases, and edge cases — that's where most bugs hide."
💡 เสริมว่าคุณ review acceptance criteria กับ Dev/SA ก่อนเขียน test case ทุกครั้ง (Agile mindset)
TECH 02
คุณทำ SQL data validation ยังไง?
How do you perform SQL data validation?
▾
แนวทางตอบ (ไทย)
"ใน MSSQL validate หลายระดับ:
— COUNT(*) ตรวจจำนวน record ว่า insert ครบ
— SUM / AVG ตรวจตัวเลขรวมตาม business rule
— JOIN ตรวจ referential integrity ระหว่าง table
— CASE WHEN ตรวจ data transformation logic
— EXCEPT / INTERSECT เพื่อ compare expected vs. actual dataset"
"In MSSQL I validate at multiple levels: COUNT(*) for record counts, SUM/AVG for aggregated figures, JOINs for referential integrity, CASE WHEN for transformation logic, and EXCEPT/INTERSECT to compare expected vs. actual datasets."
💡 ถ้ามีตัวอย่าง query จริงจากงาน เล่าให้ฟัง 1 case จะน่าเชื่อถือมาก
TECH 03
คุณ test API ด้วย Postman ยังไง?
How do you perform API testing with Postman?
▾
แนวทางตอบ (ไทย)
"ตรวจ 5 ด้านหลัก:
1. Status code ที่ถูกต้อง (200 / 201 / 400 / 401 / 404 / 500)
2. Response body — field ครบ, type ถูกต้อง
3. Business logic — data ที่ return ตรงกับ DB
4. Error handling — message ชัดเจน ไม่ expose sensitive data
5. Response time เบื้องต้น
นอกจากนี้เขียน test script เพื่อ automate assertion และรัน collection ทั้งหมดได้"
"I check 5 dimensions: correct status codes, response body structure, business logic vs. DB, error handling without sensitive data exposure, and basic response time. I also write test scripts to automate assertions and run entire collections."
💡 เสริมว่าใช้ Environment Variables สำหรับ switch ระหว่าง Dev / Staging / Prod
TECH 04
คุณทำ performance testing ด้วย JMeter ยังไง?
How do you approach performance testing with JMeter?
▾
แนวทางตอบ (ไทย)
"ออกแบบ test plan โดยกำหนด Thread Group (จำนวน user), Ramp-up period, Loop count แล้วเพิ่ม HTTP Request Sampler ตาม user flow หลัก monitor ผ่าน Aggregate Report ดู throughput, avg response time, error rate เมื่อพบ bottleneck จะ report พร้อม threshold เช่น response > 3s เมื่อ concurrent user เกิน 100"
"I design a test plan with Thread Groups (user count), Ramp-up period, and Loop count, then add HTTP Request Samplers for the main user flow. I monitor via Aggregate Report tracking throughput, avg response time, and error rate. Bottlenecks are reported with specific thresholds — e.g., response > 3s at 100+ concurrent users."
💡 Startup สนใจตัวเลข baseline — ถ้ามีประสบการณ์จริง บอก concurrent load ที่เคย test ได้เลย
TECH 05
คุณทำ mobile testing ยังไง?
How do you approach mobile application testing?
▾
แนวทางตอบ (ไทย)
"ครอบคลุม 4 ด้านหลัก:
1. Functional — flow หลักทำงานถูกต้อง
2. UI/UX — layout บนหน้าจอหลายขนาด, font ไม่ตัด, tap target เหมาะสม
3. Multi-device — Android หลาย version และ iOS
4. Network condition — slow 3G, offline — app handle gracefully หรือ crash
รวมถึง test permission (camera/location/notification) และ memory เบื้องต้น"
"I cover 4 areas: functional flows, UI/UX across screen sizes, multi-device on Android and iOS, and network conditions (slow 3G/offline). I also test permissions and run basic memory checks."
💡 ถ้า startup มี mobile product — นี่คือ differentiator ของคุณจาก QA ที่ทำแค่ web
TECH 06
อธิบายความแตกต่าง Smoke / Sanity / Regression
Explain the difference between Smoke, Sanity, and Regression testing.
▾
แนวทางตอบ (ไทย)
Smoke test: ตรวจว่า "ระบบเปิดติดไหม" เช็ค critical path เร็วๆ ก่อนว่าควรทดสอบต่อหรือเปล่า

Sanity test: ตรวจหลัง bug fix ว่า feature ที่แก้ทำงานถูกต้อง โดยไม่ต้องรัน full suite

Regression test: re-test ระบบทั้งหมดหรือส่วนที่เกี่ยวข้อง เพื่อแน่ใจว่าการแก้ code ใหม่ไม่ทำให้ feature เดิมพัง
Smoke: The "does it turn on?" check before investing in full testing.

Sanity: After a bug fix — confirm the fixed feature works without a full suite run.

Regression: Re-test the full system to ensure new changes haven't broken existing functionality.
💡 เสริมว่าที่ W2S คุณทำ regression testing ก่อน release ทุกครั้ง แสดงว่าใช้จริงไม่ใช่แค่จำ
TECH 07
Dev บอก "ไม่ใช่ bug" คุณจัดการยังไง?
How do you handle "it's not a bug" from a developer?
▾
แนวทางตอบ (ไทย)
"จะไม่เถียงทันที แต่ใช้ evidence เป็นหลัก:
1. แนบ screenshot/video + steps to reproduce ที่ชัดเจน
2. ระบุว่า behavior นี้ขัดกับ requirement / acceptance criteria ตรงไหน
3. ถ้า requirement ไม่ชัด จะ loop SA เข้ามา clarify ร่วมกัน
4. ถ้ายังขัดแย้ง จะยก user impact ให้เห็น — 'ถ้า user เจอแบบนี้จะเกิดอะไรขึ้น'"
"I don't argue directly — I lead with evidence: screenshot/video + steps to reproduce, then point to which acceptance criteria this violates. If requirements are ambiguous, I loop in the SA. If still disputed, I frame it as user impact."
💡 Startup เน้น culture of respect — แสดงว่าคุณ "collaborate" ไม่ใช่ "confront"
TECH 08
คุณทำ root cause analysis ยังไงเมื่อเกิด production issue?
How do you perform root cause analysis?
▾
แนวทางตอบ (ไทย)
"ขั้นตอน:
1. Reproduce ใน environment ที่ใกล้เคียง production
2. ดู application log หา error/exception ที่เกี่ยวข้อง
3. Query database ตรวจ data state ในช่วงเวลาที่เกิดปัญหา
4. สร้าง event timeline ดูลำดับก่อน-หลัง
5. สรุป root cause + แนะนำ preventive measure"
"My process: reproduce in a production-like environment → examine logs for errors → query the database for data state at the time of issue → build an event timeline → summarize root cause + recommend preventive measures."
💡 เสริมว่า document ทุก production issue ใน Jira เพื่อเป็น knowledge base ของทีม
🏗 วิธีคิดแบบ Startup QA
Startup ต้องการ QA ที่ "shift-left" คือเข้าร่วมตั้งแต่ design/planning ไม่ใช่แค่ test ท้ายสุด ใช้คำว่า "ผม/หนูช่วยป้องกัน defect ตั้งแต่ต้น" แทน "ผม/หนูหา bug" — ฟังดู ownership มากกว่ากันมาก
⭐ จุด unique ของคุณจากประสบการณ์
คุณมี combination ที่หายาก ในคนเดียว:

SQL Validation API Testing Performance Mobile QA Root Cause Analysis

ส่วนใหญ่ QA junior ทำได้แค่ 1-2 ด้าน เน้นจุดนี้ให้ชัดโดยเฉพาะใน startup ที่ต้องการคนทำงานได้กว้าง
🗣 Keywords ที่ควรใช้ในการสัมภาษณ์
ฝึกพูดคำเหล่านี้ให้คล่อง แสดง engineering maturity:

shift-left testing regression suite test coverage CI/CD integration defect triage acceptance criteria risk-based testing test pyramid

Startup Tech มักสัมภาษณ์ผสม TH+EN ถ้า interviewer ถามภาษาอังกฤษ ตอบภาษาอังกฤษได้เลย
⏱ โครงสร้างเวลาในการตอบ
HR question: 1.5–2 นาทีต่อคำถาม ไม่ควรยาวกว่านี้

Technical question: 2–3 นาที สามารถ think aloud ได้ บอก "ขอคิดสักครู่" ได้เลย

ถ้าไม่รู้คำตอบ: พูดว่า "ผม/หนูยังไม่เคยเจอ scenario นี้โดยตรง แต่จะ approach แบบนี้..." ดีกว่าเงียบหรือตอบผิดมาก
📋 สิ่งที่ต้องเตรียมก่อนวันสัมภาษณ์
1. รีเสิร์ชบริษัท: product คืออะไร, ปัญหาที่ solve คืออะไร, tech stack ที่ใช้
2. เตรียม 3 เรื่องเล่า STAR จากงานจริง: bug สำคัญ / ทำงานภายใต้ pressure / ทำงานกับทีม
3. อ่าน JD อีกครั้ง — keyword ไหนตรงกับ resume นำมาเล่าใน interview
4. เตรียมคำถามถามกลับ 2-3 ข้อ (ดูหัวข้อ HR 08)
5. ทดลองพูด mock answer เสียงดังคนเดียวอย่างน้อย 1 รอบ
😊 Mindset ในวันสัมภาษณ์
Interview คือ two-way conversation ไม่ใช่การสอบ คุณก็กำลัง evaluate บริษัทด้วยเช่นกัน

ความมั่นใจมาจากการเตรียมตัว ไม่ใช่จากการรู้ทุกอย่าง ถ้าเจอคำถามที่ไม่รู้ — แสดง reasoning process ออกมา นั่นคือสิ่งที่ interviewer ดูจริงๆ ไม่ใช่แค่คำตอบที่ "ถูก"
